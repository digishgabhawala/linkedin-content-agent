# linkedin-content-agent

Local-first tool that turns "what I worked on" into a LinkedIn post: brief →
clarify → draft (local LLM, scored against explicit quality gates, with
automatic recalibration) → lock → on-brand character illustration → manual
review and posting. Uses a consistent mascot character for visual branding,
generated by the sibling project
[`character-forge-v2`](../character-forge-v2), which this tool depends on
directly (spawned as a subprocess for every image render, with a callback
when it's done). Everything else -- understanding the brief, writing and
grading the post, deriving what the illustration should show -- runs against
a local Ollama model, no cloud dependency.

The first version is being built and tested for one specific use case (a
long-time software engineer building a LinkedIn presence), but that's a
starting test case, not the intended ceiling -- the brief→draft→illustrate
loop itself isn't tied to any one voice, seniority level, or industry.

## Use case

1. You tell it, in your own words, what you did. It infers a **category**
   (technical deep-dive, milestone, lessons-learned, ...) that drives how the
   draft gets graded later -- a debugging story and a celebratory ship post
   shouldn't be judged on the same curve.
2. If the brief is thin, it asks a focused follow-up question to get at
   least one real, checkable detail -- it will not invent specifics that
   weren't given to it. Capped at `CLARIFY_MAX_TURNS` (5) questions as a
   safety valve, but the real gate is downstream: see step 3.
3. It writes a draft, then **scores it** against explicit quality bars before
   you ever see it -- factual accuracy and voice authenticity are hard gates
   (must clear 9/10, never traded off), plus optimization pillars like hook
   strength, structure, length fit, and topic resonance. A rewrite-fixable
   low score triggers automatic recalibration (up to 3 passes); a score that
   no rewrite can fix (not enough real material, or the wrong angle
   entirely) escalates back to you immediately, with a specific ask, instead
   of quietly shipping a thin post as if it succeeded. See
   [CONTENT_QUALITY_DESIGN.md](CONTENT_QUALITY_DESIGN.md) for the full
   design and [TESTING.md](TESTING.md) for how it was verified.
4. You can revise it with a free-text instruction ("shorter hook", "more
   technical"), or start over, as many times as you want -- every version is
   kept, and every edit is re-scored so what's on screen always matches the
   displayed pillar scores.
5. When you lock a draft, it derives a terse visual scene description for
   the character illustration (e.g. "presenting a chart on a whiteboard,
   calm confident energy"). Recurring backdrops (an office, a home desk, ...)
   get saved once as a **named asset** and referenced with a short `@name`
   token in later scenes (e.g. `@office`) instead of repeating the full
   description -- editing an asset's text later retroactively applies to
   every post that references it. You can edit the scene text before
   rendering, insert an existing `@name` via the backdrop dropdown, or
   manage the whole asset library from the sidebar panel.
6. Generating the image is a real 15-40 min local render (via
   character-forge-v2 + ComfyUI) -- the app doesn't block on it; you can
   leave and come back.
7. Once the image is ready, review text + image together. You can still edit
   the scene prompt and regenerate (e.g. "drop the cube, keep everything
   else") before marking the post ready. Posting to LinkedIn itself is
   manual (copy the text, download the image) -- this tool doesn't publish
   anything for you.
8. You can leave feedback at any stage. It's stored, but **not yet fed back**
   into future drafts -- see Upcoming below for why.

## Prerequisites

- Python 3.10+, Node 18+
- [Ollama](https://ollama.com) running locally with `qwen3:14b` pulled:
  ```bash
  ollama pull qwen3:14b
  ```
- **[`character-forge-v2`](../character-forge-v2) set up and working**,
  including its own prerequisite (a running ComfyUI with the right models --
  see that repo's README for install instructions), since this app spawns it
  as a subprocess for every image render. At least one character must
  already have a locked `hero.png` (the shipped default, `gtee_dev`, is
  already seeded there).
- Ports `11000` (backend) and `11001` (frontend) free.

## Setup

**Backend:**
```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env      # defaults work out of the box on this machine
.venv/bin/uvicorn app.main:app --port 11000
```

**Frontend** (separate terminal):
```bash
cd frontend
npm install
npm run dev
# -> http://localhost:11001
```

Open `http://localhost:11001` and start with a brief.

## Configuration

All backend config lives in `backend/.env` (see `.env.example`). Everything
here is **relative to the current working directory when you start uvicorn**
(i.e. `backend/`, per the Setup instructions above) unless noted otherwise --
nothing is written to a fixed system path.

| Key | Default | What it does |
|---|---|---|
| `OLLAMA_URL` | `http://localhost:11434` | Ollama server |
| `OLLAMA_MODEL` | `qwen3:14b` | model used for clarify/draft/regenerate/scene |
| `DB_PATH` | `posts.db` | SQLite file, created at `backend/posts.db` on first run |
| `GENERATED_DIR` | `generated` | rendered images + placeholder, at `backend/generated/` -- pure output, safe to delete, gets rebuilt |
| `DEFAULT_CHARACTER_ID` | `gtee_dev` | which character-forge-v2 character to use -- see note below |
| `CLARIFY_MAX_TURNS` | `5` | hard cap on clarify questions -- a safety valve, not the real quality gate (see "Content quality pipeline" below) |
| `CHARACTER_FORGE_V2_PATH` | *(auto-resolved absolute path)* | only set if your layout differs from the standard sibling-directory tree |
| `COMFYUI_ENV_PYTHON` | *(auto-resolved absolute path)* | same |
| `IMAGE_CALLBACK_BASE_URL` | `http://localhost:11000` | where the forge2 subprocess POSTs back to when done |
| `IMAGE_STALL_TIMEOUT_MINUTES` | `40` | past this with no callback, the UI flags the render as possibly stalled |

`CHARACTER_FORGE_V2_PATH`/`COMFYUI_ENV_PYTHON` resolve automatically to the
correct absolute sibling paths (computed from this file's own location) --
you should not need to touch them unless you've moved things around.

**On `DEFAULT_CHARACTER_ID`:** this is a character's permanent, stable ID
(e.g. `gtee_dev`) -- not a hero-candidate filename like `hero_3000.png`.
Those are two different things in character-forge-v2: during character
creation, several candidate hero images get generated with seed-based
filenames (`hero_1000.png`, `hero_1003.png`, ...) purely so you can compare
and pick one; once picked, the WINNING candidate is copied to that
character's permanent `hero.png`, and from then on only the stable
`character_id` matters -- the seed/filename of whichever candidate got
chosen has no ongoing significance.

## Content quality pipeline

Full design in [CONTENT_QUALITY_DESIGN.md](CONTENT_QUALITY_DESIGN.md); short
version:

- **Category** (`agents/category_agent.py`) is inferred once per post from
  the brief and drives pillar weighting -- a technical deep-dive and a
  trending hot-take aren't graded on the same curve (`agents/taxonomy.py`).
- **Gates** (`factual_integrity`, `voice_authenticity`) must clear 9/10,
  never traded off against a strong hook or good structure.
- **Optimization pillars** (hook, structure, CTA, length fit, character
  consistency, topic resonance, profile fit, market timeliness) are scored
  and weighted per category, then recalibrated toward higher automatically
  (up to `max_recalibration_passes`, default 3).
- `length_fit` is scored **deterministically** from actual character count,
  not by the judge LLM -- the judge scored clearly-short drafts 8-10/10 in
  every live test even with the target spelled out in its rubric; length is
  measurable, so it isn't left to LLM judgment.
- A failure a rewrite genuinely can't fix (not enough real material, or the
  wrong angle entirely) escalates to you immediately instead of burning
  automatic passes -- including a **thin-material gate**: if the brief plus
  clarification total under ~300 characters of real substance, it stops
  after one honest best-effort draft and asks for more, rather than
  presenting a thin post as if it succeeded.
- The judge (`agents/judge_agent.py`) is the same Ollama model
  (`qwen3:14b`), a distinct system prompt, framed as reviewing someone
  else's work at lower temperature -- see the design doc for why a second
  model wasn't used.

## Known issues / operational notes

- **Image generation is genuinely slow (15-40 min)** and depends entirely on
  character-forge-v2/ComfyUI being healthy -- see that repo's README for the
  RAM-pressure and stale-ComfyUI-state failure modes found during testing.
  If a render comes back with a solid-black/corrupted image despite
  `image_ready` status, the underlying render failed silently; there is
  currently **no automatic detection of this** (see Upcoming).
- **Retrying a failed image, or regenerating a technically-successful one,
  assigns a fresh seed automatically** -- reusing the same seed would just
  replay ComfyUI's cached (possibly corrupted) result instead of rendering
  again. This is handled for you; you don't need to do anything manually.
- Only one image can render at a time (single-GPU pipeline) -- starting a
  second one while one is in flight returns a 409.
- Pillar weights in `taxonomy.py` are reasonable starting defaults, not
  calibrated against real data yet -- expect to revisit once there's a body
  of real drafts to tune against.

## Upcoming / backlog (not built yet)

- **Feedback consumption.** Feedback is captured (stage, note, timestamp)
  but deliberately not yet fed back into prompts or pillar weighting --
  different post categories likely need different feedback semantics, and
  designing that taxonomy before seeing real feedback data would be
  guessing. Ship capture, observe, design later.
- **Pre-flight RAM check** and **automatic corrupted-image detection +
  ComfyUI auto-restart** -- shared backlog items with character-forge-v2,
  see that repo's README for detail.
- **Distinct per-character personas beyond one shared personality field.**
  `character_profile` (the mascot's personality) is now a real input to both
  drafting and scoring (`character_consistency` pillar) -- not just scene
  derivation -- but the original vision of multiple characters with distinct
  POVs (e.g. one that asks security questions, one that asks ROI questions)
  hasn't been built.
- **Multi-character support beyond the one seeded character (`gtee_dev`).**
- **Multi-tenant user profiles.** `user_profile.md` is a single file by
  design (see CONTENT_QUALITY_DESIGN.md) -- the shape supports adding a
  second profile as a second file later, but there's no config/storage
  layer for N profiles yet.
- **Calibrate pillar weights against real data** once there's a body of
  real drafts to tune against (see Known issues above).

## Project layout

```
backend/app/
  config.py                    -- Settings (env-driven, see table above)
  db/models.py                  -- Post, PostDraft, Feedback, SceneAsset (SQLAlchemy)
  agents/category_agent.py      -- infer_category (brief -> category, Ollama)
  agents/taxonomy.py            -- categories, gate/optimization pillars, weights, weighted_score
  agents/draft_agent.py         -- clarify_turn, generate_draft, regenerate_draft (Ollama)
  agents/judge_agent.py         -- score_post -- grades a draft against every pillar (Ollama)
  agents/scene_agent.py         -- derive_scene (post text -> terse visual scene, Ollama)
  agents/content_sources.py     -- loads content_config/*.md (profile, skill, examples)
  services/post_service.py      -- Post state machine (clarify, draft+score+recalibrate, lock,
                                    scene assets)
  services/image_service.py     -- subprocess.Popen spawn + callback receiver + stall detection
  services/feedback_service.py  -- capture-only create/list
  api/routes.py                  -- all HTTP routes, including /api/internal/image-callback
  main.py                        -- FastAPI app, mounts /generated
backend/content_config/
  user_profile.md, skill.md, example_posts.md, scene_examples.md -- WHO/HOW inputs to
    drafting + scene derivation, see CONTENT_QUALITY_DESIGN.md
backend/tests/                   -- pytest coverage for the deterministic logic (see TESTING.md)

frontend/src/
  App.tsx                        -- top-level state-machine controller
  api.ts, types.ts                -- typed client matching routes.py exactly
  hooks/usePostPolling.ts         -- 3s polling, only while status === image_queued
  components/                     -- one component per Post.status (see App.tsx), plus
    PillarScores.tsx, SceneAssetsPanel.tsx, BackdropInsertDropdown.tsx for the quality/
    scene-asset UI
```

Post status flow: `clarifying → [needs_input ↔ drafting] → locked →
image_queued → image_ready | image_failed → ready`
