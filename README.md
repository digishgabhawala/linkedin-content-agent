# linkedin-content-agent

Local-first tool that turns "what I worked on" into a LinkedIn post: brief →
clarify → draft (local LLM, scored against explicit quality gates, with
automatic recalibration) → lock → on-brand character illustration → manual
review and posting. Uses a consistent mascot character for visual branding,
generated by the sibling project [`character-forge-v2`](../character-forge-v2).

Image generation is decoupled through the sibling
[`task-queue`](../task-queue) service rather than spawned as a local
subprocess: this app submits a task and polls for the result (piggybacking
on the frontend's existing 3s status poll, no separate background worker
needed here), and a `character-forge-v2` worker running *anywhere* --
this machine, a friend's laptop, a Colab GPU session -- claims and completes
it. See `task-queue`'s README for why (mainly: running ComfyUI and Ollama
in the same process repeatedly caused RAM contention and crashes; this
lets each heavy workload run wherever it actually has room). **Text
generation goes the same way:** understanding the brief, writing and grading
the post, and deriving the illustration's scene are `text_generation` tasks
(see `backend/app/services/llm_client.py`). This app never calls an LLM
itself; the worker on your laptop runs them (Ollama today) one task at a
time, so a draft never competes with a render for memory.

**Every request that needs compute is asynchronous: one queue task per
step.** Creating a post, answering a question, redrafting, locking and
rendering each submit just their first step and return immediately. The
app itself is the caller that decides every next step (category -> clarify
-> draft -> judge -> rewrite/escalation -> ...) when it sees a step finish,
in `backend/app/services/steps.py`. The UI's status polling is what
advances a post; a failed step shows **Retry step** (never retried
automatically). Plain reads/writes (list, open, edit scene, accept draft)
stay direct. *Known limitation:* a post only advances while someone has it
open -- close the tab mid-draft and it continues from where it paused the
next time you open it.

The first version is being built and tested for one specific use case (a
long-time software engineer building a LinkedIn presence), but that's a
starting test case, not the intended ceiling -- the brief→draft→illustrate
loop itself isn't tied to any one voice, seniority level, or industry.

## Use case

1. You tell it, in your own words, what you did. It infers a **category**
   (technical deep-dive, milestone, lessons-learned, ...) that drives how the
   draft gets graded later -- a debugging story and a celebratory ship post
   shouldn't be judged on the same curve.
2. If the brief is thin, it asks a focused follow-up question to get at
   least one real, checkable detail -- it will not invent specifics that
   weren't given to it. Capped at `CLARIFY_MAX_TURNS` (5) questions as a
   safety valve, but the real gate is downstream: see step 3.
3. It writes a draft, then **scores it** against explicit quality bars before
   you ever see it -- factual accuracy and voice authenticity are hard gates
   (must clear 9/10, never traded off), plus optimization pillars like hook
   strength, structure, length fit, and topic resonance. A rewrite-fixable
   low score triggers automatic recalibration (up to 3 passes); a score that
   no rewrite can fix (not enough real material, or the wrong angle
   entirely) escalates back to you immediately, with a specific ask, instead
   of quietly shipping a thin post as if it succeeded. See
   [CONTENT_QUALITY_DESIGN.md](CONTENT_QUALITY_DESIGN.md) for the full
   design and [TESTING.md](TESTING.md) for how it was verified.
4. You can revise it with a free-text instruction ("shorter hook", "more
   technical"), or start over, as many times as you want -- every version is
   kept, and every edit is re-scored so what's on screen always matches the
   displayed pillar scores.
5. When you lock a draft, it derives a terse visual scene description for
   the character illustration (e.g. "presenting a chart on a whiteboard,
   calm confident energy"). Recurring backdrops (an office, a home desk, ...)
   get saved once as a **named asset** and referenced with a short `@name`
   token in later scenes (e.g. `@office`) instead of repeating the full
   description -- editing an asset's text later retroactively applies to
   every post that references it. You can edit the scene text before
   rendering, insert an existing `@name` via the backdrop dropdown, or
   manage the whole asset library from the sidebar panel.
6. Generating the image submits a task to the queue and is a real 15-40 min
   render once some worker picks it up (character-forge-v2 + ComfyUI, running
   wherever) -- the app doesn't block on it; you can leave and come back.
7. Once the image is ready, review text + image together. You can still edit
   the scene prompt and regenerate (e.g. "drop the cube, keep everything
   else") before marking the post ready. Posting to LinkedIn itself is
   manual (copy the text, download the image) -- this tool doesn't publish
   anything for you.
8. You can leave feedback at any stage. It's stored, but **not yet fed back**
   into future drafts -- see Implementation TODO below for why.

## Prerequisites

- Python 3.10+, Node 18+
- **The local worker running on your laptop** (task-queue's
  `workers/local_worker.py`) -- it does both text (Ollama with `qwen3:14b`
  pulled: `ollama pull qwen3:14b`) and images. This backend itself needs no
  Ollama; with no text-capable worker online, drafting fails fast with
  "No worker can generate text right now".
- **A [`task-queue`](../task-queue) instance to submit image work to** --
  either run one locally (see that repo's README) or point `TASK_QUEUE_URL`
  at `https://ai-bharatiya-web.vercel.app/queue`. This app only
  submits tasks and polls for results; it never talks to ComfyUI directly.
- **At least one image worker actually claiming tasks**, somewhere -- this
  machine, a friend's laptop, a Colab GPU session
  (`task-queue/workers/image_worker.py`, which shells out to a local
  `character-forge-v2` + ComfyUI). Without a worker polling, submitted
  tasks just sit `queued` forever -- there's no error for this, since from
  the queue's point of view that's a perfectly valid state. At least one
  synced characters carry their locked hero URL plus complete CharacterCard
  in every image task. The worker downloads/caches that remote hero, so it
  no longer needs `workspace/<id>/hero.png` locally. Older unsynced character
  rows retain the original local-workspace fallback.
- Ports `11000` (backend) and `11001` (frontend) free.

## Setup

**Backend:**
```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env      # defaults work out of the box on this machine
.venv/bin/uvicorn app.main:app --port 11000
```

Once per mascot, copy it into the database and Storage with
`scripts/sync_character.py` (see "The mascot lives in the database" below).

**Frontend** (separate terminal):
```bash
cd frontend
npm install
npm run dev
# -> http://localhost:11001/linkedin/
```

Open `http://localhost:11001/linkedin/` and start with a brief. The API lives
under `/api/linkedin/` (the same paths as on the shared domain).

## Configuration

All backend config lives in `backend/.env` (see `.env.example`). Everything
here is **relative to the current working directory when you start uvicorn**
(i.e. `backend/`, per the Setup instructions above) unless noted otherwise --
nothing is written to a fixed system path.

| Key | Default | What it does |
|---|---|---|
| `STEP_MAX_WAIT_MINUTES` | `60` | How long a queued step (text or image) may wait for a worker before it expires; then **Retry step** |
| `DATABASE_URL` | *(unset -> SQLite at `DB_PATH`)* | where the app's data lives -- any SQLAlchemy URL, e.g. the Supabase pooler `postgresql+psycopg://...:6543/postgres` |
| `DB_SCHEMA` | `linkedin` | Postgres schema for this app's tables (keeps them apart from other apps in the same Supabase project); ignored for SQLite |
| `DB_PATH` | `posts.db` | SQLite file used only when `DATABASE_URL` is unset |
| `DEFAULT_CHARACTER_ID` | `gtee_dev` | which character-forge-v2 character to use -- see note below |
| `CLARIFY_MAX_TURNS` | `5` | hard cap on clarify questions -- a safety valve, not the real quality gate (see "Content quality pipeline" below) |
| `TASK_QUEUE_URL` | `http://127.0.0.1:8000` | canonical queue product URL; production uses `https://ai-bharatiya-web.vercel.app/queue`, which maps to `/api/queue` automatically |
| `IMAGE_STALL_TIMEOUT_MINUTES` | `40` | flags an unusually long queue wait or render runtime separately; render time starts only when a worker claims the task (independent of the task-queue lease/reclaim mechanism) |

**Database location is configuration.** Point `DATABASE_URL`/`DB_SCHEMA` at
a different project or schema and restart; the app creates the schema and
tables (and adds any newer columns) on startup. To bring existing data
along, copy it once (refuses to run if the target already has rows):

```bash
cd backend
.venv/bin/python scripts/copy_sqlite_to_postgres.py --source sqlite:///posts.db
# --target defaults to DATABASE_URL, --schema to DB_SCHEMA
```

**The mascot lives in the database, not on disk.** The backend never reads
`character-forge-v2`: the mascot's complete CharacterCard, personality and
content-addressed locked-hero identity come from the `characters` table,
with the image in a public Supabase Storage bucket. Image tasks carry a
snapshot of that data, allowing any enrolled worker to download/cache the
same hero instead of requiring a matching local forge workspace.
Copy a mascot in once, and again whenever it changes, from the machine that
has `character-forge-v2` (the service key stays on that machine; the
backend never needs it):

```bash
cd backend
SUPABASE_URL=https://<project-ref>.supabase.co SUPABASE_SERVICE_KEY=<service key> \
  .venv/bin/python scripts/sync_character.py gtee_dev
# --forge-path defaults to ../../character-forge-v2, --bucket to STORAGE_BUCKET or "linkedin"
```

Without a row, drafts lack the mascot's voice and placeholder; rendering
falls back to the legacy worker-local Character Forge workspace.

**On `DEFAULT_CHARACTER_ID`:** this is a character's permanent, stable ID
(e.g. `gtee_dev`) -- not a hero-candidate filename like `hero_3000.png`.
Those are two different things in character-forge-v2: during character
creation, several candidate hero images get generated with seed-based
filenames (`hero_1000.png`, `hero_1003.png`, ...) purely so you can compare
and pick one; once picked, the WINNING candidate is copied to that
character's permanent `hero.png`, and from then on only the stable
`character_id` matters -- the seed/filename of whichever candidate got
chosen has no ongoing significance.

## Deploying (Vercel)

One Vercel project (`linkedin-content-agent`) serves both the API and the
built frontend from the same FastAPI function -- one origin, no CORS. Config:
`vercel.json` (framework `fastapi`, region `hnd1` = Tokyo, next to the
Supabase database; the build command builds `frontend/dist`) and the root
`pyproject.toml` (Python dependencies for Vercel's `uv`, kept in sync with
`backend/requirements.txt`; entrypoint `backend.app.main:app`).

```bash
npx vercel deploy          # preview (behind Vercel's own login)
npx vercel deploy --prod   # production
```

Environment (Production and Preview; never the browser):

| Key | Value |
|---|---|
| `DATABASE_URL` | Supabase transaction pooler (port 6543) |
| `DB_SCHEMA` | `linkedin` |
| `TASK_QUEUE_URL` | `https://ai-bharatiya-web.vercel.app/queue` |
| `TASK_QUEUE_API_KEY` | this app's raw service key |
| `AUTH_ENABLED` | `true` |
| `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` | the shared Supabase project |
| `AUTH_ALLOWED_EMAILS` | who may sign in (comma list) |
| `AUTO_INIT_DB` | `false` -- no schema checks on every cold start |

**Paths.** The app is served at `/linkedin/` and its API at
`/api/linkedin/`, exactly as on `aibharatiya.com`, so the parent site
forwards paths unchanged (`/` redirects to `/linkedin`; `/linkedin` and `/linkedin/` both serve the app;
unknown paths under `/linkedin/` load the app):

```text
/linkedin            -> https://linkedin-content-agent-mauve.vercel.app/linkedin
/linkedin/:path*     -> https://linkedin-content-agent-mauve.vercel.app/linkedin/:path*
/api/linkedin/:path* -> https://linkedin-content-agent-mauve.vercel.app/api/linkedin/:path*
```

**Schema changes:** the hosted app never creates tables or columns. Before
deploying a change that adds any, run `.venv/bin/python scripts/init_db.py`
from `backend/` with `DATABASE_URL` pointing at production.

## Content quality pipeline

Full design in [CONTENT_QUALITY_DESIGN.md](CONTENT_QUALITY_DESIGN.md); short
version:

- **Category** (`agents/category_agent.py`) is inferred once per post from
  the brief and drives pillar weighting -- a technical deep-dive and a
  trending hot-take aren't graded on the same curve (`agents/taxonomy.py`).
- **Gates** (`factual_integrity`, `voice_authenticity`) must clear 9/10,
  never traded off against a strong hook or good structure.
- **Optimization pillars** (hook, structure, CTA, length fit, character
  consistency, topic resonance, profile fit, market timeliness) are scored
  and weighted per category, then recalibrated toward higher automatically
  (up to `max_recalibration_passes`, default 3).
- `length_fit` is scored **deterministically** from actual character count,
  not by the judge LLM -- the judge scored clearly-short drafts 8-10/10 in
  every live test even with the target spelled out in its rubric; length is
  measurable, so it isn't left to LLM judgment.
- A failure a rewrite genuinely can't fix (not enough real material, or the
  wrong angle entirely) escalates to you immediately instead of burning
  automatic passes -- including a **thin-material gate**: if the brief plus
  clarification total under ~300 characters of real substance, it stops
  after one honest best-effort draft and asks for more, rather than
  presenting a thin post as if it succeeded.
- The judge (`agents/judge_agent.py`) is the same Ollama model
  (`qwen3:14b`), a distinct system prompt, framed as reviewing someone
  else's work at lower temperature -- see the design doc for why a second
  model wasn't used.

## Known issues / operational notes

- **Full-quality image generation can take roughly 30 minutes on a clean
  machine or 2+ hours under memory pressure** and depends entirely on
  a worker actually claiming and processing the task -- see `task-queue`'s
  README for the queue/lease mechanics, and character-forge-v2's README for
  the RAM-pressure and stale-ComfyUI-state failure modes found during
  testing on the worker side. If a render comes back with a
  solid-black/corrupted image despite `image_ready` status, the underlying
  render failed silently; there is currently **no automatic detection of
  this** (see Implementation TODO).
- **Retrying a failed image, or regenerating a technically-successful one,
  assigns a fresh seed automatically** -- reusing the same seed would just
  replay ComfyUI's cached (possibly corrupted) result instead of rendering
  again. This is handled for you; you don't need to do anything manually.
- **No local single-flight guard on this app's side anymore** -- submitting
  image generation for multiple posts just creates multiple queued tasks;
  how many render concurrently depends entirely on how many workers are
  polling. The old "409 if one's already in flight" guard made sense when
  this app owned a single local GPU directly; now that's the task-queue's
  concern (and, transitively, however many workers you've got running),
  not this app's.
- Pillar weights in `taxonomy.py` are reasonable starting defaults, not
  calibrated against real data yet -- expect to revisit once there's a body
  of real drafts to tune against.

## Implementation TODO

- [x] Show the five-stage content journey, distinguish a queued image from
  an actively claimed/rendering task, and serialize UTC timestamps with an
  explicit timezone so browser elapsed times are correct.
- [x] Show whether the local image worker and ComfyUI are both online.
- [x] All LLM calls run as task-queue `text_generation` tasks on the local
  worker (which owns Ollama and unloads its model when idle or before a
  render); no direct Ollama access from this app.
- [x] Before image submission, check the image worker's reported free memory
  (14 GB for full quality) and show its top three memory consumers; offer
  rescan, full quality anyway, or Lightning mode when it is short. The
  worker measures its own machine and enforces the limit: a Full render it
  can't fit fails with `insufficient_memory:`, shown with a **Retry with
  Lightning** button. It never switches profile on its own.
- [x] Carry the selected generation profile explicitly through the task
  payload so the worker executes the user's choice.
- [x] Add hosted worker registration, one-minute heartbeats, coarse task
  progress, rolling lease renewal, and a read-only task-queue admin UI.
- [x] Blank/uniform renders are detected (character-forge-v2 exit code 3 ->
  worker `corrupt_output:` failure) and shown as "The image came back blank"
  with the manual Retry button (fresh seed). No automatic retry.
- [x] Worker-status hardening: a malformed task-queue reply reads as
  "Task queue unreachable"; relative-time labels tolerate unparseable dates;
  Retry repeats the last requested profile (stored as `image_profile`).
- [x] Header badge and image progress read hosted task-queue worker status
  (heartbeats, coarse stage, lost-worker detection) instead of a local
  process check.

- **Feedback consumption.** Feedback is captured (stage, note, timestamp)
  but deliberately not yet fed back into prompts or pillar weighting --
  different post categories likely need different feedback semantics, and
  designing that taxonomy before seeing real feedback data would be
  guessing. Ship capture, observe, design later.
- **Worker controls.** You start the image worker by hand; it now starts,
  idle-stops and restarts ComfyUI itself (see task-queue README). Worker
  pause/drain/shutdown controls from this UI are intentionally not in scope.
- **Distinct per-character personas beyond one shared personality field.**
  `character_profile` (the mascot's personality) is now a real input to both
  drafting and scoring (`character_consistency` pillar) -- not just scene
  derivation -- but the original vision of multiple characters with distinct
  POVs (e.g. one that asks security questions, one that asks ROI questions)
  hasn't been built.
- **Multi-character support beyond the one seeded character (`gtee_dev`).**
- **Multi-tenant user profiles.** `user_profile.md` is a single file by
  design (see CONTENT_QUALITY_DESIGN.md) -- the shape supports adding a
  second profile as a second file later, but there's no config/storage
  layer for N profiles yet.
- **Smaller stored images.** Renders are ~0.9 MB 1024x1024 PNGs; saving
  them as WebP (done in the worker before upload) would cut that ~5x.
  Not urgent: Supabase free tier's 1 GB holds ~1,000 images and we expect
  50-100 live at a time.
- **Hero candidate creation as a worker task.** Add a task-queue task type
  (e.g. `character_creation`) whose worker runs character-forge-v2's
  setup flow, generates the mascot's hero image and uploads it, so the
  app fills the `characters` row from the result. This replaces the
  one-time `scripts/sync_character.py` for new (per-user) mascots.
  Remote consumption of an already-locked hero is complete; generation,
  review and locking are the next vertical slices.
- **Image archival / cleanup.** Superseded renders (Retry, new image) stay
  in Storage unreferenced; add archival of old posts and removal of
  orphaned images.
- **Calibrate pillar weights against real data** once there's a body of
  real drafts to tune against (see Known issues above).

## Project layout

```
backend/app/
  config.py                    -- Settings (env-driven, see table above)
  db/models.py                  -- Post, Character, PostDraft, Feedback, SceneAsset (SQLAlchemy)
  agents/category_agent.py      -- infer_category (brief -> category, via llm_client)
  agents/taxonomy.py            -- categories, gate/optimization pillars, weights, weighted_score
  agents/draft_agent.py         -- clarify_turn, generate_draft, regenerate_draft (via llm_client)
  agents/judge_agent.py         -- score_post -- grades a draft against every pillar (via llm_client)
  agents/scene_agent.py         -- derive_scene (post text -> terse visual scene, via llm_client)
  agents/content_sources.py     -- loads content_config/*.md (profile, skill, examples)
  services/post_service.py      -- Post state machine (clarify, draft+score+recalibrate, lock,
                                    scene assets)
  services/image_service.py     -- submits image_generation tasks to task-queue, polls for
                                    results (sync_image_task, called from GET /posts/{id})
  services/feedback_service.py  -- capture-only create/list
  services/character_sync.py    -- mascot -> Storage + `characters` row (scripts/sync_character.py)
  api/routes.py                  -- all HTTP routes
  main.py                        -- FastAPI app
backend/content_config/
  user_profile.md, skill.md, example_posts.md, scene_examples.md -- WHO/HOW inputs to
    drafting + scene derivation, see CONTENT_QUALITY_DESIGN.md
backend/tests/                   -- pytest coverage for the deterministic logic (see TESTING.md)

frontend/src/
  App.tsx                        -- top-level state-machine controller
  api.ts, types.ts                -- typed client matching routes.py exactly
  hooks/usePostPolling.ts         -- 3s polling, only while status === image_queued
  components/                     -- one component per Post.status (see App.tsx), plus
    PillarScores.tsx, SceneAssetsPanel.tsx, BackdropInsertDropdown.tsx for the quality/
    scene-asset UI
```

Post status flow: `clarifying → [needs_input ↔ drafting] → locked →
image_queued → image_ready | image_failed → ready`
